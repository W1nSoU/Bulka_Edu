# Design: Додавання типів посад РЦ та ОФІС, фільтрація та закріплення за адміністратором

**Дата створення:** 2026-09-24  
**Статус:** Схвалено користувачем  

---

## 1. Мета та контекст

У системі з'являються два нових типи посад:
- **РЦ** (Розподільчий центр)
- **ОФІС** (Офіс)

Разом з існуючими типами посад (**ТЗ** — Торговий зал, **ВВ** — Власне виробництво) тепер доступні 4 типи:
1. `🏪 ТЗ`
2. `🍞 ВВ`
3. `📦 РЦ`
4. `🏢 ОФІС`

Конкретні посади для РЦ та ОФІС до бази даних автоматично не додаються (вони будуть створені адміністратором вручну через інтерфейс).

Головні задачі:
1. Оновити вибір типу при створенні посади (сітка 2х2).
2. Замінити кнопку перемикання типу в картці посади на виклик підменю зміни типу (сітка 2х2 з позначкою `✅` на поточному типі).
3. Додати новий фільтр користувачів у меню фільтрів: кнопка `🏷️ За типом`, яка дозволяє переглядати користувачів відповідного типу (`ТЗ`, `ВВ`, `РЦ`, `ОФІС`) зі стандартною пагінацією.
4. Закріплення стажерів РЦ та ОФІС за адміністратором:
   - Стажери з посадами напрямків `РЦ` та `ОФІС` підпорядковуються адміністратору (`creator_id`), який створив для них посилання.
   - Територіальні керівники (`ТЗ` або `ВВ`) не курують стажерів та посади `РЦ` та `ОФІС`.

## 2. Архітектурні зміни та компоненти

### 2.1. Константи (`bot/constants.py`)
Централізуємо типи посад та їх відображення:
```python
POSITION_TYPES = {
    "ТЗ": "🏪 ТЗ",
    "ВВ": "🍞 ВВ",
    "РЦ": "📦 РЦ",
    "ОФІС": "🏢 ОФІС",
}
VALID_POSITION_TYPES = tuple(POSITION_TYPES.keys())
```

### 2.2. Рівень бази даних (`database/positions.py` та `database/users.py`)
1. **`database/positions.py`**:
   - `add_position(name, days_count, territorial_type="ТЗ")`: валідує `territorial_type in VALID_POSITION_TYPES`.
   - `update_territorial_type(position_id, new_type)`: дозволяє значення `VALID_POSITION_TYPES`.
   - `get_position_direction(role_name)`: повертає значення `territorial_type` з таблиці `positions` (зокрема `"РЦ"` та `"ОФІС"`).
2. **`database/users.py`**:
   - Додаємо функцію `get_users_by_position_type(territorial_type: str) -> list[dict]`:
     ```sql
     SELECT u.* FROM users u
     JOIN positions p ON u.role = p.name
     WHERE p.territorial_type = ?
     ORDER BY u.last_activity DESC
     ```
     Для повної сумісності також підтримується вибірка за ролями, що відповідають поточному мапінгу позицій.

### 2.3. Сервісний шар (`bot/services/positions.py`)
- `update_position_type(position_id: int, new_type: str) -> bool`:
  - Перевіряє `new_type in VALID_POSITION_TYPES`.
  - Оновлює запис у БД та повертає `True`/`False`.
- `add_position(name, days_count, territorial_type)`:
  - Підтримує передачу всіх 4 типів.

### 2.4. Інтерфейс у боті (`bot/menus/developer.py`)

#### А. Створення посади:
- У `_dev_pos_prompt_type`:
  - Кнопки типів у сітці 2х2:
    - Рядок 1: `[ 🏪 ТЗ ]` `[ 🍞 ВВ ]` (callback `dev_pos_add_type:ТЗ`, `dev_pos_add_type:ВВ`)
    - Рядок 2: `[ 📦 РЦ ]` `[ 🏢 ОФІС ]` (callback `dev_pos_add_type:РЦ`, `dev_pos_add_type:ОФІС`)
    - Рядок 3: `[ ❌ Скасувати ]` (callback `dev_positions_menu`)
- У `dev_pos_add_type_callback`:
  - Додає посаду з вибраним типом.
  - Повідомлення: `✅ Посаду <b>{pos_name}</b> ({days} днів, {type_label}) успішно додано!`.

#### Б. Картка посади (`dev_pos_view`):
- Відображає `🏷 <b>Тип:</b> {type_label}`.
- Замість бінарного перемикача додається кнопка:
  `[ 🏷 Змінити тип ]` (callback `dev_pos_type_menu:{pos_id}`).

#### В. Меню зміни типу посади:
- Хендлер `dev_pos_type_menu`:
  - Показує інлайн-клавіатуру 2х2 з 4 типами.
  - Поточний тип посади має позначку `✅` (наприклад, `🏪 ТЗ ✅`) і `callback_data="ignore"`.
  - Інші три типи мають callback `dev_pos_set_type:{pos_id}:{code}`.
  - Кнопка повернення: `[ 🔙 Назад до посади ]` (callback `dev_pos_view:{pos_id}`).
- Хендлер `dev_pos_set_type`:
  - Викликає `update_position_type(pos_id, new_type)`.
  - Відправляє повідомлення `callback.answer(f"✅ Тип змінено на {label}")`.
  - Перемальовує картку посади з оновленими даними.

#### Г. Фільтр користувачів за типом:
- В `_users_filters_keyboard`:
  - Додаємо кнопку `🏷️ За типом` (callback `dev_users_by_type`) у другий рядок поруч із `👔 За керівниками`.
- Хендлер `developer_users_by_type_menu`:
  - Виводить клавіатуру вибору типу: `[ 🏪 ТЗ ]` `[ 🍞 ВВ ]`, `[ 📦 РЦ ]` `[ 🏢 ОФІС ]`, `[ ⬅️ Назад ]`.
- Хендлер `developer_users_filter_type`:
  - Отримує користувачів через `get_users_by_position_type(t_type)`.
  - Якщо користувач — територіал (не адмін), фільтрує за містом територіала та відповідним типом.
  - Відображає через `_developer_show_users_list(callback, users, f"🏷️ <b>Користувачі: {type_label}</b>", f"type:{t_type}", 0)`.
- Пагінація `developer_users_pagination_handler`:
  - Обробляє префікс `dev_users_pag:type:{type_code}:{page}`.

## 3. Логіка підпорядкування стажерів РЦ та ОФІС

1. **Створення інвайт-посилання (`developer_users_add_role`):**
   - Визначається напрямок обраної ролі через `get_position_direction(role)`.
   - Якщо напрямок ролі `РЦ` або `ОФІС`:
     - Керівником автоматично стає адміністратор, який створює посилання: `target_supervisor_uid = creator_id`.
     - `extra_data = {"creator_id": creator_id, "target_manager_id": creator_id}`.
     - У підсумковому повідомленні про створене посилання пишеться: `👤 Закріплено за: <b>Адміністратор (ви)</b>`.
2. **Реєстрація користувача (`bot/handlers.py`):**
   - Перевіряється напрямок посади стажера. Якщо це `РЦ` або `ОФІС`, `assigned_manager_id` призначається безпосередньо на `creator_id` або `target_manager_id`.
   - Запобігається автоматичне закріплення за керівником магазину (`shop_mgr`) або територіалом міста (`get_appropriate_territorial_for_user`).
3. **Ізоляція територіалів (`database/managers.py`):**
   - У `find_best_territorial_for_city`: якщо напрямок ролі належить до `("РЦ", "ОФІС")`, функція повертає `None`.
