3. **Гарантувати повноту знаходження терміна («знайти усе, що є по X»):**

## 3. Архітектура та модулі

### 3.1. Парсинг, чанкінг і дедуплікація (`bot/services/knowledge_chunker.py`)

Окремий чистий модуль без мережевих побічних ефектів:

- **`extract_clean_text(raw_content: str, content_type: str) -> str`**:
  - Ігнорує записи з `content_type` in `("test", "photo_files", "video_files")` (повертає `""`).
  - Якщо `raw_content` є JSON-масивом `[{"text": ..., "photo": ...}]` (аналогічно `_parse_material_content` у `bot/handlers.py`), витягує лише непорожні значення `"text"` (або рядки списку), з'єднуючи їх через `\n\n`. Поля `"photo"` / `"video"` та медіа-ідентифікатори `AgACAg...` повністю відкидаються.
  - Нормалізує переноси рядків та зайві пробіли.
- **`split_into_chunks(text: str, target_chars: int = 750, overlap_chars: int = 120) -> list[str]`**:
  - Ділить текст на смислові чанки орієнтовно `600-900` символів з перекриттям `~120` символів.
  - Пріоритет розбиття: межа абзаців (`\n\n`), далі перенос рядка (`\n`), далі кінець речення (`. `, `! `, `? `), далі пробіл. Якщо окремий абзац довший за `900` символів, ріжеться по реченнях із збереженням перекриття.
- **`compute_chunk_hash(text: str) -> str`**:
  - Нормалізує пробіли/регістр-стійку канонічну форму (зберігаючи оригінал для відображення GPT, але хешуючи нормалізовані пробіли `re.sub(r"\s+", " ", text.strip())`) -> SHA-256 hex digest.
- **`build_deduplicated_chunks(materials: list[dict]) -> list[dict]`**:
  - Проходить по всіх матеріалах, ігнорує порожній чистий текст (`len(clean) < 10`).
  - Для порожнього `role` (`""` або `None`) призначає службову мітку джерела `display_role = "Загальні матеріали"` і `scope_role = "__UNASSIGNED__"`, щоб такий матеріал не заважав Stage 1 конкретної посади, але був доступний у глобальному пошуку та Stage 2.
  - Об'єднує однакові `chunk_hash` в один запис з масивом `sources`: `[{"material_id": int, "role": str, "day": int, "title": str}]` (без дублювання однакових трійок `(role, day, material_id)`).

### 3.3. Гібридний пошук та індексація (`bot/services/semantic_search.py`)

Переписуємо `bot/services/semantic_search.py` під чистий Python + OpenAI `text-embedding-3-small`:

1. **Індексація та авто-синхронізація (`sync_knowledge_index` / `build_and_reset_embeddings`):**
   - `build_and_reset_embeddings()` (вже викликається з `bot/menus/developer.py` при збереженні матеріалів і буде викликатись у фоні при старті з `main.py`) формує дедупліковані чанки з `get_all_materials()`, синхронізує `material_chunks` і для чанків без ембедінга пакетно (батчами по 50) викликає `client.embeddings.create(model="text-embedding-3-small", input=...)`.
   - Захист від розсинхрону: перед пошуком перевіряється легкий відбиток таблиці `materials` (`COUNT(*)` + `MAX(updated_at)` + порівняння з поточною БД). Якщо `material_chunks` порожня або матеріали змінились (редагування, видалення, перейменування посади), інкрементальний `sync_knowledge_index()` виконується автоматично перед пошуком. Якщо OpenAI Embeddings API недоступний під час синку, текст і `sources` все одно зберігаються, а пошук працює на лексичному + Exact-Token шарі.
2. **Токенізація та легкий український стемінг:**
   - Токенізатор виділяє слова довжиною `>= 2` символів (українські літери з апострофом, латиниця, цифри). Видаляє базові стоп-слова (`що`, `як`, `де`, `чи`, `та`, `і`, `в`, `на`, `по`, `про`, `для`, `це`, `коли`, `чи`). Якщо після видалення стоп-слів список порожній (наприклад, запит із самих коротких слів), залишає всі вихідні токени `>= 2`.
   - Стеммер `uk_stem(token)` обрізає типові флективні/суфіксальні закінчення українських слів (лише для слів довжиною `>= 5`, щоб короткі слова/абревіатури на кшталт `"рц"`, `"тз"`, `"вв"`, `"чек"`, `"каса"` не спотворювались).
3. **Обов'язковий Exact-Token Scan (повнота збігів):**
   - Для кожного значимого токена запиту будуємо перевірку:
     - точний збіг слова по межах (`(?<![\wа-яіїєґ'])<token>(?![\wа-яіїєґ'])`, case-insensitive) - критично для коротких слів на кшталт `РЦ`, щоб не плутати з `"серце"`;
     - для слів `>= 5` символів додатково збіг за основою (`uk_stem(q_tok) == uk_stem(c_tok)` або префікс `>= 5` символів).
   - Усі чанки в активному скоупі, що мають точне входження хоча б одного значимого токена (або частку збіглих токенів `>= 0.5` для багатослівних запитів, і `== 1.0` для 1-2-слівних), позначаються як `is_exact_match = True` з `exact_hit_count`.
4. **Гібридний скоринг і відбір у контекст GPT (`MAX_CONTEXT_CHARS = 35000`):**
   - Якщо OpenAI налаштований і чанки мають `embedding`, рахуємо ембедінг запиту (`text-embedding-3-small`) і косинусну подібність у чистому Python (`_cosine_similarity(v1, v2)`).
   - Рахуємо нормований лексичний скор (`lexical_score in [0, 1]` на основі покриття стемів запиту + бонус точного входження фрази/підрядка).
   - Фінальний скор чанка:
     - при наявності векторів: `0.60 * vector_score + 0.40 * lexical_score + (0.25 якщо є exact_token_match)`;
     - при відсутності векторів (fallback): `lexical_score + (0.25 якщо exact_token_match)`.
   - **Формування контексту без втрати речень (рішення для запитів типу `"РЦ"`):**
     1. Беремо до **10** найкращих чанків за `final_score` (повним текстом).
     2. Далі перевіряємо **всі решта чанків у скоупі, де `is_exact_match == True`** (сортовані за кількістю збіглих токенів та `final_score`). Кожен такий чанк теж додається у контекст у межах `MAX_CONTEXT_CHARS = 35000`:
        - якщо чанків небагато і текст вміщається - беремо повний чанк;
        - якщо згадок дуже багато або чанки великі - вирізаємо з чанка **конкретні абзаци чи вікно речень (`±2` сусідніх речення) навколо кожного входження токена**, щоб гарантувати доставку в GPT усіх релевантних речень по темі без втрат.

### 3.4. 2-етапний пошук і GPT-синтез (`bot/services/openai_ai.py`)

Переробляємо `ask_gpt_tutor(...)` (і залишаємо зворотну сумісність сигнатури або оновлюємо виклик у `bot/handlers.py`):

1. **Визначення скоупів:**
   - Функція `_filter_chunks_by_role(chunks, role_filter)`:
     - Якщо `role_filter is None`: повертає всі чанки мережі (`mode = "global"` або `"Всі посади"`).
     - Якщо `role_filter` задано: повертає чанки, у `sources` яких є `role == role_filter` або `role == "ALL"`.
2. **Виконання 2-етапного сценарію:**
   - **Якщо `role_filter is None`:** одразу виконуємо гібридний пошук по всій мережі -> синтез GPT (або екстрактивний фолбек без GPT).
   - **Якщо `role_filter` задано:**
     - **Етап 1 (лише своя посада + `'ALL'`):**
       - Відбираємо чанки посади `role_filter` + `'ALL'`.
       - Якщо кількість чанків `> 0` І гібридний пошук знаходить принаймні один кандидат з мінімальним порогом релевантності (`is_exact_match == True` або `vector_score >= 0.25` або `lexical_score >= 0.20`):
         - Викликаємо GPT з інструкцією відповідати **тільки** на основі наданих фрагментів, максимально повно перелічивши всі відповідні правила з джерелами `[День X]`.
         - Якщо в наданих фрагментах цієї посади реально немає відповіді на питання користувача, GPT має повернути чіткий маркер `__NO_ANSWER_IN_MATERIALS__`.
         - Якщо GPT дав змістовну відповідь -> повертаємо її **одразу** (`used_network_fallback = False`), інші посади НЕ зачіпаємо.
     - **Етап 2 (автоматичний перехід на всю мережу):**
       - Спрацьовує **тільки якщо** Етап 1 не дав відповіді з однієї з 3 причин:
         1. У цієї посади `0` текстових чанків у базі (як `Комплектувальник-приймальник`);
         2. У Етапі 1 жоден кандидат не пройшов мінімальний поріг релевантності;
         3. GPT повернув `__NO_ANSWER_IN_MATERIALS__` по матеріалах Етапу 1.
       - Запускаємо гібридний пошук **по всіх чанках мережі** (виключаючи вже перевірені чанки Етапу 1, якщо GPT вже відхилив їх як нерелевантні, або залишаючи повний набір для повноти).
       - Формуємо відповідь GPT з явним зазначенням по кожному пункту, з якої посади та якого дня взято інформацію (`[Посада, День X]`), і додаємо на початок прозоре пояснення для працівника:
         `ℹ️ <i>У матеріалах твоєї посади відповіді не знайдено, тому я перевірив інструкції всієї мережі:</i>`
       - Якщо навіть по всій мережі нічого не знайдено (або GPT теж повернув `__NO_ANSWER_IN_MATERIALS__`), чесно повідомляємо, що інформації за запитом не знайдено в базі знань.
3. **Формат виводу GPT і безпека Telegram HTML:**
   - Системний промпт суворо забороняє вигадувати факти та зобов'язує узагальнити **усі** знайдені в наданих фрагментах правила/речення по запиту (без пропуску пунктів з кінця контексту).
   - Дозволені лише валідні для Telegram HTML теги (`<b>`, `<i>`, `<code>`, `<blockquote>`) без непідтримуваних тегів на кшталт `<ul>`, `<ol>`, `<li>`, `<p>`, `<br>`, які ламають `parse_mode="HTML"`. Додатково проганяємо вихід через безпечну HTML-нормалізацію перед відправкою в Telegram.

   - Додаємо helper `_get_remind_searchable_roles(exclude_manager_roles: bool = False) -> list[str]`:
     - Об'єднує унікальні назви посад із `get_all_positions()` та `get_unique_roles_from_materials()` (без порожніх рядків та `'ALL'`).
     - Якщо користувач є лише керівником (без прав HR/Dev/Observer), відфільтровує службові `"Керівник"`, `"Керівник Стажер"`.
   - Замість індексів по статичному `AVAILABLE_ROLES`, зберігаємо `remind_roles_list = roles` у FSM state і в `callback_data` передаємо `remind_role_select:{idx}` (короткий індекс у межах FSM-списку, гарантовано вміщується у 64 байти Telegram), а `remind_role_select_callback` бере роль із `data.get("remind_roles_list")` (з безпечним фолбеком на повторний виклик `_get_remind_searchable_roles`, якщо FSM було перезавантажено).

3. **`bot/menus/manager.py` - `manager_remind_menu` та `manager_process_remind_role`:**
   - Додаємо кнопку `🌐 Всі посади` (`callback_data="mgr_remind_role:ALL"`) в `manager_remind_menu`, а також підтягуємо ролі з `_get_manager_add_roles()` + будь-які не-менеджерські ролі з `materials` (щоб не губились посади, по яких вже є матеріали).
   - У `manager_process_remind_role` обробляємо `"ALL"` -> `role = None`, зберігаючи `mode="manager_global"`.
   - У `process_keyword_search` оновлюємо обробку `mode == "manager_global"` так само без втрати `role_filter = None`.

4. **`main.py`:**
   - Додаємо фоновий старт індексації чанків та ембедінгів через `asyncio.create_task(build_and_reset_embeddings())` при старті бота (замість генерації невикористовуваних `summary` у `backfill_materials_summaries_background`, щоб не витрачати OpenAI-токени на застарілий 2-кроковий роутер).

## 4. Обробка помилок та крайові випадки

- **OpenAI API повернув 401/429/таймаут або `OPENAI_API_KEY` відсутній:**
  - `sync_knowledge_index()` логує попередження, але зберігає текстові чанки в SQLite без векторів.
  - Пошук автоматично перемикається на Pure-Lexical + Exact-Token режим по очищених чанках і повертає користувачу зрозумілу відповідь із цитатами (`[Посада, День X]`) замість мовчазного фейлу чи сирого JSON.
- **Одиночні/дуже короткі запити (`"РЦ"`, `"ВВ"`, `"ТЗ"`):**
  - Стоп-слова не зрізають такі токени; Exact-Token Scanner гарантує 100% збіг по межах слова, і збіги не губляться серед інших чанків.
- **Співробітник без матеріалів (наприклад, `Комплектувальник-приймальник`):**
  - Етап 1 одразу бачить `0` власних чанків і автоматично запускає Етап 2 по всій мережі без помилок і без порожніх відповідей.
- **Посада є в БД, але має 10+ однакових копій тексту у 5 ролях:**
  - Дедуплікація зводить їх до 1 чанка зі списком джерел, не перевищуючи контекст і не спотворюючи частотне ранжування.
- **Довгі відповіді понад 4000 символів:**
  - Коректне розбиття тексту на частини або безпечна відправка без обриву незакритих HTML-тегів (`<b>`, `<i>`).

## 5. План тестування

У `tests/test_remind_topic_hybrid_search.py` (з ізольованою тимчасовою SQLite БД та моками OpenAI API):

1. **Парсинг, чанкінг та дедуплікація:**
   - JSON `[{"text": "...", "photo": "AgACAg..."}]` очищається від `photo` ID; `content_type == "test"` та `"photo_files"` виключаються.
   - Ідентичні фрагменти з різних посад об'єднуються в один `chunk_hash` зі списком усіх джерел.
2. **Інкрементальний кеш ембедінгів у SQLite:**
   - Перший синк обчислює ембедінги; повторний запуск на незмінених матеріалах робить `0` запитів до OpenAI Embeddings API. Зміна одного матеріалу перераховує лише змінені чанки; видалення матеріалу видаляє застарілі чанки.
3. **Повнота Exact-Token + Гібридного пошуку:**
   - Запит `"Списування алкоголю"` знаходить чанк Дня 1 (а не зупиняється на Дні 4).
   - Запит `"РЦ"` знаходить усі згадки `"РЦ"` у різних інструкціях (включаючи малі речення всередині великих текстів і понад Top-10 чанків), водночас не чіпляючи слово `"серце"`.
4. **2-етапна логіка (власна посада -> вся мережа):**
   - Якщо у посади користувача є відповідь (Stage 1) - мережеві матеріали інших посад НЕ домішуються.
   - Якщо у посади `0` матеріалів (`Комплектувальник-приймальник`) або Stage 1 дає `__NO_ANSWER_IN_MATERIALS__` - автоматично підтягуються матеріали інших посад з позначкою джерела.
   - Глобальний пошук (`role_filter=None`) одразу шукає по всій мережі.
5. **UI, ролі та `mode="dev_test"`:**
   - `process_keyword_search` з `mode="dev_test"` і `role=None` ("Всі посади") не підставляє `'Developer'` і шукає глобально.
   - Меню вибору ролі показує динамічні ролі з `positions` і `materials` (наприклад, `Керівник ТТ`, `Комплектувальник-приймальник`), без жорсткої прив'язки до `AVAILABLE_ROLES`.
6. **Відмовостійкий фолбек без OpenAI:**
   - При помилці/відключенні OpenAI API користувач отримує чисті текстові фрагменти без JSON-ключів.
7. **Регресійний прогін:** `pytest` для нових тестів і пов'язаних тестів у `tests/` (`test_manager_dynamic_roles.py`, `test_materials_pagination.py`, `test_position_types.py`).
