# Дизайн: Керування магазинами та органічна міграція бази даних

**Дата:** 2026-09-22  
**Статус:** Схвалено користувачем  
**Ціль:** Надати адміністраторам повноцінне меню керування торговими точками (магазинами) в меню «Інше», перевести зберігання магазинів з хардкоду (`bot.constants.AVAILABLE_SHOPS`) у SQLite-базу даних, забезпечити пагінацію по 6 штук на сторінку з фільтрацією за містами, редагування прив'язок, безпечне видалення з обов'язковим переведенням працівників, та гарантувати 100% збереження існуючих зв'язків користувачів при деплої.

---

## 1. Архітектура бази даних та міграція

### 1.1 Таблиця `shops` у `database/users.db`
Таблиця створюється в основній базі `users.db` поруч з `users` та `cities`:
```sql
CREATE TABLE IF NOT EXISTS shops (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT UNIQUE NOT NULL,
    city TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 1.2 Органічний Auto-Seed без втрати даних
При першому старті бота функція `init_shops_db()`:
1. Перевіряє наявність записів у `shops`.
2. Якщо таблиця порожня: автоматично імпортує всі 25 магазинів з `bot.constants.AVAILABLE_SHOPS` зі збереженням точного формату назв (`"B-19 вул. Героїв Маріуполя, 62"`, `"B-31 вул. Юрія Руфа, 5"` тощо).
3. Оскільки в базі `users.db` користувачі вже мають точні назви магазинів у колонці `users.shop`, а в `managers.db` вони зберігаються в JSON-колонці `shops`, **жодна існуюча прив'язка не постраждає**.

### 1.3 Операції з базою (`database/shops.py`)
- `get_cities_with_shops() -> list[dict]`: повертає міста та кількість магазинів у кожному.
- `get_shops_by_city(city: str) -> list[dict]`: повертає магазини міста за алфавітом/назвою.
- `get_shop_by_id(shop_id: int) -> dict | None`: повертає магазин за `id`.
- `get_shop_by_name(name: str) -> dict | None`: пошук магазину за назвою.
- `add_shop(name: str, city: str) -> tuple[bool, str]`: додавання магазину з валідацією унікальності назви.
- `rename_shop(shop_id: int, new_name: str) -> tuple[bool, str]`: каскадне оновлення старої назви на нову в:
  - `shops.name`
  - `users.shop`
  - `managers.shops` (парсинг JSON-масиву, заміна та серіалізація назад)
  - `tokens.shop`
  - `training_events.shop`
- `change_shop_city(shop_id: int, new_city: str) -> tuple[bool, str]`: перенесення магазину в інше місто (з каскадним оновленням `users.city`).
- `count_users_in_shop(shop_name: str) -> int`: кількість співробітників (стажерів та працівників), закріплених за магазином.
- `delete_shop_and_transfer_users(shop_id: int, transfer_to_shop_name: str | None) -> tuple[bool, str]`:
  - Якщо за старим магазином закріплені користувачі — переводить їх у `transfer_to_shop_name`.
  - Видаляє магазин із `shops`.
  - Видаляє магазин зі списку `shops` у `managers.db`.
- `get_shop_manager(shop_name: str) -> dict | None`: знаходить керівника, у списку `shops` якого є цей магазин.
- `set_shop_manager(shop_name: str, new_manager_uid: int | None) -> bool`: закріплює магазин за обраним керівником або відкріплює його.

## 2. Інтерфейс користувача та FSM-діалоги

### 2.1 Точка входу
В `_admin_other_keyboard` (`bot/menus/developer.py`) додається кнопка:
`[ 🏪 Магазини ]` (`callback_data="dev_shops_cities_menu"`).

### 2.2 Екран 1: Вибір міста
- Заголовок: `🏪 <b>Управління магазинами</b>\nОберіть місто:`
- Інлайн-кнопки міст із лічильником магазинів, наприклад:
  - `[ Хмельницький (13) ]` (`callback_data="dev_shops_city:Хмельницький:1"`)
  - `[ Камʼянець-Подільський (12) ]` (`callback_data="dev_shops_city:Камʼянець-Подільський:1"`)
- Нижні кнопки:
  - `[ ➕ Додати магазин ]` (`callback_data="dev_shop_add"`)
  - `[ 🔙 Назад ]` (`callback_data="dev_main_other"`)

### 2.3 Екран 2: Пагінація магазинів міста (по 6 штук)
- Заголовок: `🏪 <b>Магазини: {city}</b>\n(Сторінка {page}/{total_pages})`
- Кнопки: по 1 кнопці на магазин у рядку для повної читабельності:
  - `[ B-19 вул. Героїв Маріуполя, 62 ]`
  - `[ B-17 проспект Миру, 69 ]`
  - ... (до 6 штук на сторінці)
- Рядок навігації:
  - `[ ⬅️ ] [ 1/3 ] [ ➡️ ]`
- Нижні кнопки:
  - `[ ➕ Додати магазин ]`
  - `[ 🔙 До списку міст ]`

### 2.4 Екран 3: Картка магазину
- Текст картки:
  ```text
  🏪 <b>Магазин:</b> B-19 вул. Героїв Маріуполя, 62
  🏙 <b>Місто:</b> Хмельницький
  👔 <b>Керівник:</b> Бондар Олександр (@bondar_o)
  👥 <b>Працівників / стажерів:</b> 5 осіб
  ```
- Кнопки дій:
  - `[ ✏️ Змінити назву ]` ➡️ FSM вводу нової назви
  - `[ 🏙 Змінити місто ]` ➡️ вибір нового міста з доступних
  - `[ 👔 Змінити керівника ]` ➡️ інлайн-список керівників міста + кнопка «Зняти керівника»
  - `[ 🗑 Видалити магазин ]` ➡️ перевірка закріплених осіб
  - `[ 🔙 До списку магазинів ]`

### 2.5 Сценарій видалення магазину
1. Система рахує `count = count_users_in_shop(shop_name)`:
   - **Якщо `count == 0`**:
     Показується підтвердження:
     `Ви дійсно бажаєте видалити магазин «{name}»? Закріплених працівників немає.`
     Кнопки: `[ ❌ Так, видалити ]` / `[ Скасувати ]`.
   - **Якщо `count > 0`**:
     Показується попередження:
     `⚠️ У магазині «{name}» закріплено {count} співробітників.\nОберіть магазин у місті {city}, куди їх перевести перед видаленням:`
     Інлайн-список інших магазинів цього міста (з пагінацією по 6).
     Після вибору цільового магазину:
     1. Всі користувачі переносяться: `UPDATE users SET shop = new_shop WHERE shop = old_shop`.
     2. Старий магазин видаляється з `shops` та відкріплюється від керівників.
     3. Виводиться звіт: `✅ Магазин успішно видалено. {count} працівників переведено в «{new_shop}».`

### 2.6 Сценарій створення нового магазину (`dev_shop_add`)
1. Вибір міста зі списку доступних міст (`database.cities`).
2. Введення назви магазину текстовим повідомленням (FSM: `DeveloperStates.waiting_add_shop_name`).
3. Вибір керівника для цього магазину зі списку діючих керівників міста або кнопка `[ ⏩ Пропустити (без керівника) ]`.
4. Створення запису в `shops` та закріплення за керівником (якщо обрано).

## 3. План тестування (Verification Plan)
- Unit-тести `tests/test_shops_management.py`:
  1. Тест ініціалізації та auto-seed з `AVAILABLE_SHOPS` (перевірка кількості та відповідності міст).
  2. Тест додавання магазину (валідація унікальності).
  3. Тест каскадного перейменування (оновлення в `users`, `managers`, `tokens`).
  4. Тест зміни міста магазину.
  5. Тест видалення порожнього магазину.
  6. Тест видалення магазину з користувачами та успішний трансфер людей до нового магазину.
  7. Тест закріплення та зміни керівника магазину.
- Повний регресійний запуск тестів проекту: `unittest discover tests`.
