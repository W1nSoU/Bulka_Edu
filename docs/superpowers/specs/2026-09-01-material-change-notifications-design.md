# Дизайн-специфікація: Оповіщення про зміну навчальних матеріалів та Аналітика ознайомлення (Пункт 8)

## 1. Загальний огляд
Коли адміністратор вносить зміни до навчальних матеріалів посади (текст, відео, фото або тести — додавання, заміна сторінок чи повне оновлення), бот надсилає посторінкове сповіщення зі зміненим контентом усім носіям цієї посади (як стажерам, так і працівникам) та всім керівникам компанії.

Розсилка здійснюється автоматичними хвилями по 40 осіб з інтервалом в 1 годину між хвилями для запобігання перевантаженню. На останній сторінці повідомлення розташовується кнопка «Зі змінами ознайомлений/а», яка при натисканні фіксує час ознайомлення та замінюється на «Ви ознайомлені зі змінами».

В розділі «Аналітика» Панелі Адміністратора додається підрозділ «Ознайомлення», в якому через 75 годин після відправки формується детальна аналітика за категоріями («Керівники», «Працівники», «Стажери»), датами змін та магазинами. Якщо користувач натиснув кнопку після 72 годин, він фіксується як ознайомлений із позначкою запізнення `⏳`.

## 2. Схема бази даних (`materials.db` / `users.db`)

### 2.1 Таблиця `material_change_events`
Зберігає метадані та збережений контент змін:
- `id` (INTEGER PRIMARY KEY AUTOINCREMENT)
- `role` (TEXT NOT NULL) — цільова посада (наприклад, "Касир", "Пекар").
- `day` (INTEGER NOT NULL) — навчальний день.
- `content_type` (TEXT NOT NULL) — тип зміни: `'text'`, `'video'`, `'photo_files'`, `'tests'`, `'insert'`, `'replace'`.
- `description` (TEXT) — опис зміни (наприклад, "Вставка сторінок 2-4").
- `pages_json` (TEXT NOT NULL) — JSON-масив змінених сторінок контенту для пагінації.
- `created_at` (TIMESTAMP DEFAULT CURRENT_TIMESTAMP) — дата та точний час запуску події.
- `status` (TEXT DEFAULT 'in_progress') — `'in_progress'` або `'completed'`.

### 2.2 Таблиця `material_change_recipients`
Зберігає стан доставки та ознайомлення для кожного користувача:
- `id` (INTEGER PRIMARY KEY AUTOINCREMENT)
- `event_id` (INTEGER NOT NULL REFERENCES material_change_events(id) ON DELETE CASCADE)
- `user_id` (INTEGER NOT NULL) — Telegram UID користувача.
- `role_type` (TEXT NOT NULL) — `'керівник'`, `'працівник'`, `'стажер'`.
- `shop` (TEXT) — назва/адреса магазину.
- `city` (TEXT) — місто.
- `wave_number` (INTEGER DEFAULT 1) — номер хвилі (1, 2, 3... по 40 осіб на хвилю).
- `status` (TEXT DEFAULT 'pending') — `'pending'`, `'sent'`, `'failed'`.
- `sent_at` (TIMESTAMP) — фактичний час відправки.
- `acknowledged_at` (TIMESTAMP) — час натискання кнопки ознайомлення.
- `is_late` (INTEGER DEFAULT 0) — 1, якщо ознайомлення відбулося пізніше ніж через 72 години від `sent_at`.
- `message_id` (INTEGER) — ID відправленого повідомлення в чаті з користувачем.

### 2.3 Автоматичне очищення (3 місяці / 90 днів)
- Функція `prune_old_material_events()` виконує `DELETE FROM material_change_events WHERE created_at < datetime('now', '-90 days')`.

## 3. Механізм хвильової розсилки (Wave Broadcaster)

### 3.1 Формування черги
1. При підтвердженні оголошення змін у Dev-панелі (`dev_notify:now` або `process_notify_message`):
   - Отримуються всі активні працівники та стажери цільової посади.
   - Отримуються всі активні керівники компанії (`process IN ('Керівник', 'Керівник Стажер')`).
   - Створюється подія в `material_change_events`.
   - Отримувачі нарізаються на батчі по 40 осіб:
     - 1-40: `wave_number = 1`, запланований час = $T_0$.
     - 41-80: `wave_number = 2`, запланований час = $T_0 + 1\text{ год}$.
     - 81-120: `wave_number = 3`, запланований час = $T_0 + 2\text{ год}$, тощо.
2. Перша хвиля відправляється негайно через фонову асинхронну задачу `asyncio.create_task(run_wave_dispatcher())`.
3. Планувальник періодично (або через таймери) перевіряє наявність незавершених хвиль і виконує їх у запланований час.
4. При перезапуску бота фоновий воркер перевіряє таблицю `material_change_recipients` і підхоплює всі `pending` хвилі відповідно до графіка.

### 3.2 Формат повідомлення та пагінація в чаті користувача
- **Текст повідомлення:**
  ```text
  📢 <b>Оновлення навчальних матеріалів</b>
  📚 Посада: <b>{role}</b> | 📅 День: <b>{day}</b>
  
  {контент поточної сторінки}
  ```
- **Клавіатура повідомлення:**
  - Якщо сторінок $> 1$:
    `[ ⬅️ ] [ 📄 {page}/{total_pages} ] [ ➡️ ]`
    *(callback: `mat_ch_pag:{event_id}:{recipient_id}:{page}`)*
  - На останній сторінці (або під єдиною сторінкою):
    - До ознайомлення: `[ 🔘 Зі змінами ознайомлений/а ]` *(callback: `mat_ch_ack:{event_id}:{recipient_id}`)*
    - Після ознайомлення: `[ ✅ Ви ознайомлені зі змінами ]` *(callback: `ignore`)*

### 3.3 Обробка натискання кнопки «Зі змінами ознайомлений/а»
- Отримується запис з `material_change_recipients`.
- Перевіряється час: якщо $T_{\text{now}} - T_{\text{sent}} > 72\text{ год}$, встановлюється `is_late = 1`.
- Записується `acknowledged_at = datetime.utcnow()`.
- Клавіатура на повідомленні оновлюється на `[ ✅ Ви ознайомлені зі змінами ]`.
- Відправляється `callback.answer("✅ Дякуємо! Ви успішно ознайомились зі змінами.", show_alert=True)`.

## 4. Інтерфейс аналітики в Панелі Адміністратора

### 4.1 Навігація
- **Шлях:** Панель Адміністратора ➔ `📊 Аналітика` ➔ кнопка `[ 📋 Ознайомлення ]` (`dev_an_ack_menu`).
- **Меню категорій:**
  - `[ 👔 Керівники ]` (`dev_ack_cat:керівник`)
  - `[ 👷 Працівники ]` (`dev_ack_cat:працівник`)
  - `[ 🎓 Стажери ]` (`dev_ack_cat:стажер`)
  - `[ ⬅️ Назад ]` (`dev_main_analyt`)

### 4.2 Вибір дати зміни
- Отримуються всі події за останні 90 днів для обраної категорії, які мають отримувачів цієї категорії.
- Формується пагінований список інлайн-кнопок (по 6 на сторінку):
  - Приклад: `📅 01.09 14:30 — Касир (День 2)`
  - Навігація при $> 6$ дат: `[ ⬅️ ] [ 📄 1/N ] [ ➡️ ]`.

### 4.3 Порогова перевірка 75 годин
- При переході на конкретну подію обчислюється $\Delta = T_{\text{now}} - T_{\text{event}}$:
  - **Якщо $\Delta < 75\text{ год}$:**
    - Відображається інформаційна картка з таймером зворотного відліку:
      ```text
      ⏳ Аналітика формується через 75 годин після запуску розсилки.
      До формування звіту залишилось: {hours} год {mins} хв.
      
      Поточний статус:
      • Всього отримувачів: {total}
      • Вже ознайомились: {ack_count}
      ```
  - **Якщо $\Delta \ge 75\text{ год}$:**
    - Відображається повна аналітична картка:
      ```text
      📊 <b>Аналітика ознайомлення</b>
      📚 Посада: <b>{role}</b> | 📅 День: <b>{day}</b>
      📝 Зміна: {description}
      🕒 Дата розсилки: {created_at}
      
      👥 Категорія: <b>{category}</b>
      • Всього: {total} осіб
      • Ознайомились: {ack_count} ({ack_percent}%)
      • Не ознайомились: {noack_count} ({noack_percent}%)
      ```
    - Кнопки перегляду:
      - `[ ✅ Ознайомились ({ack_count}) ]` (`dev_ack_sub:{event_id}:{cat}:ack`)
      - `[ ❌ Не ознайомились ({noack_count}) ]` (`dev_ack_sub:{event_id}:{cat}:noack`)
      - `[ ⬅️ Назад ]` (`dev_ack_cat:{cat}`)

### 4.4 Деталізація за магазинами
- При виборі «Ознайомились» або «Не ознайомились» формується список магазинів з кількістю осіб:
  - Кнопки: `[ 🏪 вул. Хрещатик, 1 (3 чол.) ]` з пагінацією по 6 магазинів на сторінку.
- При виборі магазину відображається список людей:
  - **Для списку ознайомлених:**
    `👤 Шевченко Тарас — 01.09 15:20`
    `👤 Франко Іван — 04.09 18:40 ⏳ (після 72 год)`
  - **Для списку неознайомлених:**
    `👤 Леся Українка — ❌ Не ознайомилась (>72 год ігнорування)`

## 5. План верифікації та тестування
1. **Тестування бази даних та черги:**
   - Створення події зміни матеріалу, генерація отримувачів та розподіл по 40 осіб на хвилю.
   - Перевірка збереження `wave_number`, `status`, `sent_at`.
2. **Тестування інтерфейсу користувача:**
   - Посторінкове повідомлення, навігація ⬅️ / ➡️.
   - Клік на «Зі змінами ознайомлений/а», оновлення кнопки на «Ви ознайомлені зі змінами», встановлення `acknowledged_at`.
3. **Тестування часових порогів (72h / 75h):**
   - Клік до 72 годин $\rightarrow$ `is_late = 0`.
   - Клік після 72 годин $\rightarrow$ `is_late = 1` (позначка ⏳).
   - Меню аналітики при часі $< 75\text{ год}$ $\rightarrow$ картка з таймером зворотного відліку.
   - Меню аналітики при часі $\ge 75\text{ год}$ $\rightarrow$ повний звіт та фільтрація по магазинах.
4. **Тестування автоматичного очищення (90 днів):**
   - Видалення подій та реципієнтів із датою створення понад 90 днів тому.
