# Дизайн-специфікація: Автоматична прив'язка працівників до Територіалів за Містом та Типом посади (ТЗ / ВВ)

**Дата:** 2026-09-01  
**Статус:** Схвалено  
**Призначення:** Забезпечення повної автоматизації закріплення працівників та стажерів за Територіальними керівниками на основі збігу міста та напрямку посади (Торговий зал `ТЗ` / Власне виробництво `ВВ`).

---

## 1. Контекст та Мета
На підприємстві в кожному місті можуть одночасно функціонувати два Територіальні керівники:
1. **Територіал ТЗ** (Торговий зал) — відповідає за працівників торгового залу (касири, продавці тощо).
2. **Територіал ВВ** (Власне виробництво) — відповідає за працівників виробничих посад (пекарі, кухарі, піцайоло тощо).

Працівники та стажери реєструються в системі із зазначенням міста (`city`) та посади (`role`).  
Потрібно, щоб:
- При додаванні або зміні посади адміністратор міг чітко обрати або змінити її тип (`ТЗ` чи `ВВ`).
- Територіали бачили виключно працівників та стажерів свого міста та свого типу посади без необхідності ручної міграції чи ручного закріплення окремих користувачів.

---

## 2. Архітектура та Модель даних

### 2.1. Таблиця `positions` (`DB_PATH`)
- Поля: `id`, `name`, `days_count`, `territorial_type` (`TEXT NOT NULL DEFAULT 'ТЗ'`), `created_at`.
- Можливі значення `territorial_type`:
  - `'ТЗ'` — Торговий зал.
  - `'ВВ'` — Власне виробництво.

### 2.2. Таблиця `managers` (`MANAGERS_DB_PATH`)
- Поля: `uid`, `username`, `full_name`, `process`, `shops`, `city`, `responsible_uid`, `territorial_type`, `status`.
- Для ролі `process = 'Територіал'`:
  - `city` вказує закріплене місто.
  - `territorial_type` вказує закріплений напрямок (`ТЗ` або `ВВ`).

### 2.3. Таблиця `users` (`DB_PATH`)
- Поля: `user_id`, `role`, `city`, `shop`, `status`, `manager_id`, `last_activity`, тощо.

## 3. Функціональні вимоги та інтерфейс

### 3.1. Додавання нової посади (`dev_pos_add`)
FSM-ланцюжок створення посади:
1. `DeveloperStates.waiting_add_position_name`: введення назви посади.
2. `DeveloperStates.waiting_add_position_days`: введення або вибір кількості днів навчання (за замовчуванням 5).
3. `DeveloperStates.waiting_add_position_type`: вибір типу посади за допомогою інлайн-кнопок:
   - `[ 🏪 Торговий зал (ТЗ) ]` (`dev_pos_add_type:ТЗ`)
   - `[ 🍞 Власне виробництво (ВВ) ]` (`dev_pos_add_type:ВВ`)
4. Збереження посади з обраними параметрами (`add_position(name, days, territorial_type)`).

### 3.2. Картка посади (`dev_pos_view`)
- Відображає поточний тип: `🏪 Торговий зал (ТЗ)` або `🍞 Власне виробництво (ВВ)`.
- Містить кнопку перемикання типу: `[ 🍞 Змінити на ВВ ]` / `[ 🏪 Змінити на ТЗ ]`.
- Зміна типу миттєво оновлює `positions.territorial_type`, що автоматично перемикає видимість усіх працівників цієї посади між територіалами ТЗ та ВВ.

### 3.3. Додавання Територіала (`dev_territorial_add`)
- Вибір UID ➔ Вибір міста ➔ Вибір типу (ТЗ / ВВ).
- Дозволяє існування двох територіалів для одного міста з різними типами (`ТЗ` та `ВВ`).

### 3.4. Фільтрація користувачів для Територіала (`_filter_users_for_territorial`)
Оновлена функція у `bot/menus/developer.py`:
1. Отримує запис територіала за `user_id` (`get_manager_by_uid(user_id)`).
2. Якщо користувач не є територіалом або є адміністратором — повертає повний список без змін.
3. Отримує `t_city = manager.get('city')` та `t_type = manager.get('territorial_type') or 'ТЗ'`.
4. Завантажує словник типів посад: `positions_map = {pos['name']: pos.get('territorial_type', 'ТЗ') for pos in await get_all_positions()}`.
5. Фільтрує список користувачів:
   ```python
   filtered = []
   for u in users:
       u_city = u.get("city")
       u_role = u.get("role")
       u_type = positions_map.get(u_role, "ТЗ")
       if u_city == t_city and u_type == t_type:
           filtered.append(u)
   ```
6. Використовується в меню активних стажерів, працівників, неактивних користувачів, аналітики та прогресу.
