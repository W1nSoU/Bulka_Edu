# Дизайн-специфікація: Оголошення про оновлення навчальних матеріалів та ознайомлення («Ознайомився»)

**Дата:** 2026-11-20  
**Проєкт:** `Bulka_Edu` (Telegram-бот корпоративного навчання)  
**Статус:** Узгоджено на етапі brainstorming

---

## 1. Мета та контекст

Коли Адміністратор оновлює навчальні матеріали будь-якої посади, бот повинен:
1. Запитати Адміністратора, чи потрібно оголосити зміну навчальних матеріалів, обʼєднати її з наступними правками у чернетку, чи зберегти без оголошення.
2. Запропонувати 2 режими оголошення:
   - **Вручну:** Адміністратор самостійно пише опис змін (текст або фото з підписом).
   - **Автоматично:** бот автоматично формує пагінацію з усіх доданих, змінених або видалених сторінок (текст, фото, відео) з бейджами змін та опціональним коротким коментарем Адміністратора зверху.
3. Показати екран превʼю (з можливістю прогортати сторінки очима користувача та точним підрахунком отримувачів і хвиль) перед стартом розсилки.
4. Розіслати оголошення цільовій аудиторії (працівники й стажери цієї посади + керівники + територіали напрямку, без наглядачів) хвилями по **40 осіб кожні 4 хвилини** з авто-відновленням після перезапуску бота.
5. Забезпечити робочу логіку ознайомлень: користувач гортає сторінки пагінацією, а на останній сторінці (або одразу, якщо сторінка одна) натискає кнопку **`🔘 Зі змінами ознайомлений/а`** -> фіксується час ознайомлення, прострочення (> 72 год) і повна аналітика + XLSX-звіт у панелі Адміністратора.

## 2. Архітектура та межі модулів

Система спирається на існуючий каркас `material_notifications.db` і розширюється без порушення зворотної сумісності зі старими подіями та XLSX-експортом:

| Модуль | Відповідальність |
|---|---|
| `database/material_notifications.py` | Схема БД (`material_change_events`, `material_change_recipients`, нова таблиця `material_change_drafts`), CRUD чернеток, підрахунок отримувачів для превʼю, запити незавершених подій для авто-відновлення хвиль, оновлення `message_id` отримувача та статусу події. |
| `bot/services/wave_broadcaster.py` | Уніфікована нормалізація сторінок (`normalize_change_page`), спільний рендерер текст/фото/відео (`send_or_edit_change_page`), побудова клавіатур, хвильова відправка (40 осіб / 240 сек), захист від дублювання задач, обробка `TelegramRetryAfter` / `TelegramForbiddenError`, авто-відновлення хвиль при старті (`resume_pending_wave_broadcasts`). |
| `bot/menus/developer.py` | Єдиний хелпер запиту оголошення `_prompt_material_change_announcement(...)`, підключений до всіх 9 точок редагування матеріалів; FSM-потік вибору дії (Оголосити зараз / Обʼєднати з наступним / Не оголошувати), режиму (Вручну / Авто + опціональний коментар), превʼю та перегляду як користувач; банер накопиченої чернетки в меню посади; оновлений рендеринг фото/відео у «📝 Зміст змін» (`dev_ack_changes`). |
| `bot/handlers.py` | Користувацька пагінація (`mat_ch_pag:`) через спільний рендерер (безпомилкове перемикання текст ↔ фото ↔ відео + оновлення `message_id` у БД при `delete+send`) та підтвердження ознайомлення (`mat_ch_ack:`). |
| `main.py` | Виклик `resume_pending_wave_broadcasts(bot)` після ініціалізації БД на старті бота. |

## 3. Модель даних

### 3.1 Нова таблиця `material_change_drafts` у `material_notifications.db`

```sql
CREATE TABLE IF NOT EXISTS material_change_drafts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    admin_id INTEGER NOT NULL,
    role TEXT NOT NULL,
    items_json TEXT NOT NULL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(admin_id, role)
)
```

- Ізолює чернетки від реальних подій у `material_change_events`, тому чернетки ніколи не потрапляють в аналітику ознайомлень чи XLSX.
- Зберігається на диску, тож переживає перехід між меню, `state.clear()` та перезапуск бота.
- При запуску розсилки чернетка по `(admin_id, role)` очищується.

### 3.2 Уніфікований формат сторінки в `pages_json` та `items_json`

```json
{
  "text": "Текст сторінки (може бути порожнім для фото/відео без підпису)",
  "photo": "Telegram file_id фото (опціонально)",
  "video": "Telegram file_id відео (опціонально)",
  "change_type": "added | modified | deleted | manual",
  "day": 1,
  "source_type": "text | photo_files | video_files | video | manual",
  "comment": "Опціональний короткий коментар Адміністратора (зберігається на 1-й сторінці в авто-режимі)"
}
```

Для `material_change_events.description` (відображається в списку подій аналітики та XLSX):
- Ручний режим: введений Адміністратором текст (або `"Фото-оголошення"`, якщо фото без підпису).
- Автоматичний режим: коментар Адміністратора (якщо доданий), інакше автоматичне зведення на кшталт `"Авто: +3 дод., 1 зм., 1 вид."`.

**Зворотна сумісність:** `normalize_change_page(raw_page, default_day=1)` перетворює старі елементи формату `str` на `{"text": raw_page, "change_type": "manual", "day": default_day, "source_type": "text"}`, а існуючі `dict` без `change_type` на `change_type="modified"`.

### 3.3 Нові функції в `database/material_notifications.py`

- `append_draft_items(admin_id: int, role: str, items: List[Dict[str, Any]]) -> int` - додає сторінки до чернетки `(admin_id, role)` і повертає нову загальну кількість сторінок.
- `get_draft_items(admin_id: int, role: str) -> List[Dict[str, Any]]` - повертає список сторінок чернетки (або `[]`).
- `clear_draft(admin_id: int, role: str) -> None` - видаляє чернетку `(admin_id, role)`.
- `get_recipients_preview_stats(role: str) -> Dict[str, int]` - повертає точну кількість унікальних отримувачів (без запису в БД) з розбивкою: `total`, `workers`, `interns`, `managers`, `territorials`, `waves`.
- `get_events_with_pending_recipients() -> List[int]` - повертає список `event_id`, де в `material_change_recipients` є записи зі `status = 'pending'`.
- `mark_event_completed_if_done(event_id: int) -> None` - якщо не залишилось `pending`-отримувачів, ставить `material_change_events.status = 'completed'`.
- `update_recipient_message_id(recipient_id: int, message_id: int) -> None` - оновлює `message_id`, якщо під час гортання між текстом і медіа повідомлення було перестворено.

## 4. Точки редагування та формування змін (усі 9 точок)

Після успішного збереження матеріалу в БД кожна з 9 точок у `bot/menus/developer.py` викликає `_prompt_material_change_announcement(...)` із точним переліком змінених сторінок:

| # | Дія Адміністратора | Хендлер у `developer.py` | Що передається як `change_items` | `change_type` |
|---|---|---|---|---|
| 1 | Додавання / повна заміна текстового матеріалу | `_finalize_material_update` | Нові сторінки `material_parts` (текст + фото) | `added` (якщо матеріалу не було) / `modified` (якщо існував) |
| 2 | Доповнення 1 сторінкою (початок / кінець / між) | `developer_process_complement_content` | Саме додана `new_page` (виправляє поточний баг втрати `new_page`) | `added` |
| 3 | Доповнення масивом сторінок | `developer_process_insert_array_done` | Масив `insert_array` | `added` |
| 4 | Заміна діапазону сторінок | `developer_process_replace_array_done` | Масив `replace_array` | `modified` |
| 5 | Виправлення конкретної сторінки (текст або фото) | `developer_process_fix_page` | Оновлена сторінка `pages[page]` | `modified` |
| 6 | Видалення сторінки | `developer_material_delete_confirm` | Видалена сторінка `removed_page` до видалення | `deleted` |
| 7 | Завантаження фото-матеріалів | `_finalize_photo_update` | Список `{"text": "", "photo": fid}` | `added` / `modified` |
| 8 | Завантаження відео-файлів | `_finalize_video_update` | Список `{"text": "", "video": fid}` | `added` / `modified` |
| 9 | Оновлення посилання на відео | `developer_process_material_video` | `{"text": f"🎥 Відео: {new_url}"}` | `added` / `modified` |

## 5. Сценарій Адміністратора (UX-флоу)

### Крок 1: Запит після збереження правки
Бот показує повідомлення:
- Посада, День, кількість змінених сторінок у поточній правці (+ якщо в `material_change_drafts` уже є накопичені сторінки по цій посаді, зазначається: `📥 У чернетці вже є N стор. - вони обʼєднаються при оголошенні`).
- Кнопки:
  - `📢 Оголосити зараз` (`dev_notify:now`)
  - `📥 Обʼєднати з наступним` (`dev_notify:merge`)
  - `🔇 Не оголошувати` (`dev_notify:none`)

Також у меню редагування матеріалів посади (вибір дня), якщо у поточного Адміністратора є непорожня чернетка по цій посаді, відображаються додаткові кнопки:
- `📢 Оголосити накопичені зміни ({N} стор.)` (`dev_draft_announce`)
- `🗑 Очистити чернетку ({N} стор.)` (`dev_draft_clear`)

### Крок 2: Вибір режиму (після «📢 Оголосити зараз»)
Поточні сторінки обʼєднуються з чернеткою (якщо вона є) у `announce_auto_pages` в FSM. Бот показує:
- `✍️ Написати самостійно` (`dev_ann_mode:manual`)
- `🤖 Автоматично (показати зміни, {N} стор.)` (`dev_ann_mode:auto`)
- `❌ Скасувати` (`dev_ann_cancel`)

### Крок 3А: Ручний режим (`manual`)
- Стан `DeveloperStates.waiting_notify_message`.
- Адмін надсилає текст або фото з підписом (1 повідомлення).
- Формується 1 сторінка `{"text": ..., "photo": ..., "change_type": "manual", "day": day, "source_type": "manual"}`.
- Перехід на **Крок 4 (Превʼю)**.

### Крок 3Б: Автоматичний режим (`auto`)
- Бот питає:
  - `💬 Додати короткий коментар зверху` (`dev_ann_comment:add`) -> стан `DeveloperStates.waiting_announce_comment` -> Адмін пише короткий вступний коментар (наприклад, «Додали інструкцію прийому яєць») -> перехід на **Крок 4**.
  - `⏭ Без коментаря (до превʼю)` (`dev_ann_comment:skip`) -> одразу перехід на **Крок 4**.
  - `⬅️ Назад` (`dev_ann_back_mode`).

### Крок 4: Екран превʼю та підтвердження
- Показує:
  - Посаду, режим (`Вручну` / `Автоматично`), кількість сторінок, коментар (якщо є).
  - Точну кількість отримувачів з `get_recipients_preview_stats(role)` (працівники, стажери, керівники, територіали).
  - План хвиль: `🌊 Хвиль: {waves} (по 40 осіб кожні 4 хв)`.
- Кнопки:
  - `👀 Переглянути як користувач` (`dev_ann_preview:0`) - відкриває інтерактивну пагінацію сторінок точно так, як їх побачить користувач, із кнопкою повернення `⬅️ До підтвердження` (`dev_ann_preview_back`).
  - `🚀 Запустити розсилку` (`dev_ann_confirm_send`) - створює подію `create_material_change_event(...)`, створює отримувачів `create_recipients_for_event(...)`, очищає чернетку `clear_draft(admin_id, role)`, запускає `start_event_wave_broadcast(bot, event_id)` і звітує Адміну.
  - `❌ Скасувати` (`dev_ann_cancel`) - повертає в меню без запуску розсилки (чернетка зберігається).

## 6. Рендеринг сторінок, Користувацька частина та Хвилі

### 6.1 Універсальний рендерер `send_or_edit_change_page(...)`
Використовується для:
1. Первинної відправки у хвилях (`send_wave_batch`)
2. Гортання в користувача (`mat_ch_pag:`)
3. Превʼю Адміна (`dev_ann_preview:`)
4. Перегляду «📝 Зміст змін» в адмін-аналітиці (`dev_ack_changes:`)

Правила форматування:
- Шапка:
  ```html
  📢 <b>Оновлення навчальних матеріалів</b>
  📚 Посада: <b>{role}</b> | 📅 День: <b>{day}</b>
  ───────────────────
  ```
- На 1-й сторінці в авто-режимі, якщо задано коментар Адміністратора:
  `💬 <b>Коментар:</b> {comment}` + порожній рядок.
- Бейдж для авто-режиму:
  - `added` -> `🆕 <b>Додано</b>`
  - `modified` -> `✏️ <b>Змінено</b>`
  - `deleted` -> `❌ <b>Видалено</b>`
  - `manual` -> без бейджа.
- Ліміти Telegram:
  - Для текстової сторінки - ліміт 4096 символів (безпечне обрізання на 4000).
  - Для фото/відео сторінки - підпис `caption` до 1024 символів (безпечне обрізання на 980 з поміткою `<i>… (повний текст у розділі «Навчання»)</i>`, щоб пагінація та кнопка «Ознайомився» завжди залишалися прикріпленими до одного повідомлення).
- Перемикання типів при `edit`:
  - `text -> text`: `edit_text`
  - `media -> media` (фото/відео): `edit_media(InputMediaPhoto / InputMediaVideo)`
  - `text <-> media` (різні типи повідомлень): `send_photo`/`send_video`/`send_message` нового повідомлення + безпечне `delete` попереднього + повернення нового `message_id` (для оновлення `material_change_recipients.message_id`).
- HTML-fallback: якщо Telegram повертає помилку парсингу HTML (`can't parse entities`), рендерер повторює спробу з `html.escape(...)` тіла сторінки.

### 6.2 Користувацька пагінація та «Ознайомився»
- Клавіатура:
  - Якщо `total_pages > 1`: `[ ⬅️ ] [ 📄 {page+1}/{total_pages} ] [ ➡️ ]` (`mat_ch_pag:{event_id}:{recipient_id}:{target_page}`).
  - Якщо `page == total_pages - 1` або `total_pages == 1`:
    - до підтвердження: `[ 🔘 Зі змінами ознайомлений/а ]` (`mat_ch_ack:{event_id}:{recipient_id}`)
    - після підтвердження: `[ ✅ Ви ознайомлені зі змінами ]` (`ignore`)
- При натисканні `mat_ch_ack:`:
  - `mark_recipient_acknowledged(event_id, user_id)` фіксує `acknowledged_at = CURRENT_TIMESTAMP` та `is_late = 1` якщо від `sent_at` минуло понад 72 години.
  - Оновлюється клавіатура поточного повідомлення (`edit_reply_markup`).
  - Показується alert: `✅ Дякуємо! Ви успішно ознайомились зі змінами.` (або з приміткою про > 72 год).

### 6.3 Хвильова розсилка (40 осіб / 4 хвилини) та авто-відновлення
- Константи у `bot/services/wave_broadcaster.py`:
  - `WAVE_BATCH_SIZE = 40`
  - `WAVE_INTERVAL_SECONDS = 240` (4 хвилини)
  - `PER_MESSAGE_DELAY_SECONDS = 0.08`
- Захист від дублів: модульний `_active_event_ids: set[int]` гарантує, що для одного `event_id` виконується не більше однієї фонової задачі.
- Обробка помилок Telegram при доставці:
  - `TelegramRetryAfter`: `await asyncio.sleep(e.retry_after + 1)` та 1 повторна спроба.
  - `TelegramForbiddenError` / будь-яка інша невиправна помилка: `mark_recipient_failed(rec_id)`, продовження хвилі без зупинки.
- По завершенні всіх хвиль: `mark_event_completed_if_done(event_id)`.
- **Авто-відновлення на старті (`main.py`):** `resume_pending_wave_broadcasts(bot)` опитує `get_events_with_pending_recipients()` і для кожного `event_id` запускає `start_event_wave_broadcast(bot, event_id)` (який відправляє лише ті хвилі, де ще залишилися `pending` отримувачі).

## 7. Верифікація та тестування

1. **Автоматичні unit/integration тести (`tests/test_material_notifications_flow.py`):**
   - Чернетки: `append_draft_items`, `get_draft_items`, обʼєднання кількох правок, `clear_draft`.
   - Нормалізація сторінок: старі `str`, нові `dict` (текст, фото, відео, `deleted`, `added`, `modified`, `manual`), форматування заголовків і бейджів, безпечне обрізання caption > 1024 символів.
   - Клавіатура користувача: кнопка «Ознайомився» відсутня на сторінках `0..N-2`, зʼявляється на сторінці `N-1` та при `total_pages == 1`, змінює стан на `✅ Ви ознайомлені зі змінами` після ack.
   - Отримувачі та хвилі: розбиття по 40 осіб, виключення `Наглядач`, фіксація `acknowledged_at` і `is_late` (> 72 год), `get_events_with_pending_recipients` і `mark_event_completed_if_done`.
   - Мок-тест хвильової відправки: захист від дублів `_active_event_ids`, обробка `TelegramForbiddenError` та відновлення незавершених хвиль.
2. **Статична перевірка:** `py_compile` для всіх змінених файлів (`database/material_notifications.py`, `bot/services/wave_broadcaster.py`, `bot/menus/developer.py`, `bot/handlers.py`, `main.py`).
